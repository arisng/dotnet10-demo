# Demo4 vs Demo4.1 Comparison (2026-01-21)

## Purpose
Capture how `demo4` (monolithic Entra ID integration) compares to `demo4.1` (distributed Entra + BFF with Aspire) across documentation messaging and project layout so we can be confident `demo4.1` builds on earlier foundations.

## Documentation differences
- `demo4/README.md` still follows the workshop template: it opens with the multi-part goal, enumerates cataloged patterns with direct links, lists the full technology stack, and points to multiple `.docs/research` write-ups, ADRs, and troubleshooting notes. It also includes a detailed architecture diagram, ``What’s New`` roster, and step-by-step getting-started + verification instructions centered on the local Blazor monolith.
- `demo4.1/README.md` shifts the narrative toward distributed orchestration: the goal and patterns sections now call out YARP, Aspire, and InteractiveAuto; the tech stack bullet list emphasizes the orchestration pieces and notes EF Core is not used; research links focus on the new Aspire/YARP decisions. The architecture summary is leaner, while the “What’s New” area explicitly cites .NET Aspire, YARP proxying, and refined token handling for weather/Graph APIs. The getting-started instructions now run `SaaS.AppHost` via Aspire and expect the Aspire dashboard rather than a single `dotnet watch` run.

## Structural/layout differences
- `demo4/` contains a single Blazor Server/WebAssembly solution (`Demo4.EntraIntegration.slnx`) with three projects (`Demo4.EntraIntegration`, `.Client`, `.Shared`) plus a `.docs/` folder and VS metadata. There is no service orchestration layer.
- `demo4.1/` introduces the Aspire-based layout: the root has `Demo41.slnx`, `.docs/`, and five SaaS* projects (`AppHost`, `Backend`, `Frontend`, `Frontend.Client`, `ServiceDefaults`, `Shared`). `SaaS.Frontend` acts as the BFF/YARP host, the frontend client is split into a separate project, and Aspire (`AppHost`/`ServiceDefaults`) orchestrates service discovery/configuration. This mirrors the workshops’ distributed modular monolith structure (demo5+ patterns).

## Progressive enhancements
1. Demo4 prioritizes hybrid authentication (local passkeys + Entra) with claims mapping plus Graph access inside the monolith.
2. Demo4.1 reuses that hybrid auth baseline but layers on YARP reverse proxying for `/api/proxy/*`, adds .NET Aspire for orchestration, and leans on InteractiveAuto semantics for the WASM client.
3. The documentation tilts accordingly: demo4 is a foundation-focused README; demo4.1 is an orchestration-focused README that documents new prerequisites (Aspire launch profile), Azure settings, and the distributed verification steps.
