# Demo 4.1 Retrospective (2025-12-21)

This note captures what went wrong while implementing/running Demo 4.1, what assumptions were incorrect, and what we learned so we can avoid the same traps next time.

## Executive Summary

We hit three unrelated but compounding issues:

1. **Aspire AppHost startup failed** because the AppHost project wasn’t using the Aspire AppHost SDK and didn’t have required dashboard/OTLP configuration (launch settings).
2. **Backend 401s were misdiagnosed as “no token / token not acquired”**, but the real root cause was **issuer validation**: the access token’s `iss` claim was `https://sts.windows.net/{tenantId}/` (v1 token) while the API was validating against the v2 issuer `https://login.microsoftonline.com/{tenantId}/v2.0`.
3. We initially assumed **`EnableTokenAcquisitionToCallDownstreamApi()` would “automatically handle everything”**. It *does* enable token acquisition services, but you still must **call `IDownstreamApi` or `ITokenAcquisition`** (and attach the token to requests in some way).

## What Actually Happened (Symptoms -> Root Cause)

### A) AppHost failed to start (Aspire orchestration)

**Symptom**

- AppHost crashed at startup with an options validation exception complaining about missing **DCP executable path** and missing **dashboard path**.

**Root cause**

- The AppHost was created as a normal console project with only NuGet references, so the project didn’t get the Aspire AppHost SDK behavior that wires up orchestration tooling metadata and dashboard defaults.

**Fix**

- Move to the Aspire AppHost SDK (`Aspire.AppHost.Sdk`) and provide dashboard settings via `launchSettings.json`.

**Official docs**

- Aspire SDK overview / using `Aspire.AppHost.Sdk`:  
  - https://learn.microsoft.com/en-us/dotnet/aspire/fundamentals/dotnet-aspire-sdk
- AppHost configuration (launchSettings + dashboard/OTLP env vars):  
  - https://learn.microsoft.com/en-us/dotnet/aspire/app-host/configuration
- Dashboard configuration from AppHost (recommended: launchSettings env vars):  
  - https://aspire.dev/dashboard/configuration/

### B) Backend API returned 401 (Unauthorized) even after successful token acquisition

**Symptom**

- Frontend logs showed MSAL successfully acquiring an access token for scope `api://.../Weather.Get`.
- Backend responded `401` and `ctx.User` was unauthenticated inside the authorization policy.

**Root cause**

- Backend JWT bearer validation failed because **issuer (`iss`) didn’t match the issuer derived from the metadata endpoint**.
  - Token `iss` was: `https://sts.windows.net/{tenantId}/`
  - Backend expected: `https://login.microsoftonline.com/{tenantId}/v2.0`

This difference is expected when the access token is a **v1 token**. Microsoft’s docs explicitly call out that Entra tokens can have either issuer format depending on token version (`ver` claim).

**Fix**

- Accept both valid issuer formats for Entra-issued access tokens in development (v2 issuer and `sts.windows.net` issuer). After this change, JwtBearer authenticated the user and the `Weather.Get` scope policy evaluated correctly.

**Official docs**

- Troubleshooting signature/issuer validation lists both issuer formats for Entra ID tokens:  
  - https://learn.microsoft.com/en-us/troubleshoot/entra/entra-id/app-integration/troubleshooting-signature-validation-errors
- Access token claims reference (`iss`, `ver`) and guidance that v2 tokens end in `/v2.0`:  
  - https://learn.microsoft.com/en-us/entra/identity-platform/access-token-claims-reference

### C) “Why didn’t `EnableTokenAcquisitionToCallDownstreamApi()` work?”

**What we expected (incorrect assumption)**

- We assumed calling `.EnableTokenAcquisitionToCallDownstreamApi()` would *implicitly* attach access tokens to outgoing HTTP requests so that calling a downstream API “just works”.

**What actually happens**

`.EnableTokenAcquisitionToCallDownstreamApi()` enables the token acquisition pipeline and adds the services used to acquire tokens for the signed-in user. It **does not** automatically add bearer tokens to *every* outgoing `HttpClient` request.

Microsoft.Identity.Web offers “don’t acquire a token yourself” *mechanisms*, but you still **use** those mechanisms explicitly:

- Use **`IDownstreamApi`** to call a downstream API (it handles acquiring the token and adding it to the call).
- Or use **`ITokenAcquisition`** to acquire the token, then attach it yourself to an `HttpClient` request (which is what we do now).

In other words, “no token acquisition code” means “use `IDownstreamApi` or Graph helpers” — not “all HttpClient calls become magically authenticated”.

**Why we ended up “manual” in `ServerWeatherForecaster`**

- During debugging, we wanted explicit control over:
  - which scopes were requested,
  - how the token was attached,
  - and how service discovery resolved the BaseUrl (`https+http://weatherapi`).
- `ITokenAcquisition` + `HttpClientFactory` made these steps visible and easier to diagnose.

It’s also important to note: **token acquisition was actually working earlier** (MSAL showed successful token retrieval). The 401 was caused by the backend’s **issuer validation mismatch**, not by `EnableTokenAcquisitionToCallDownstreamApi()` failing.

**Official docs**

- Web app calling a downstream API: recommended patterns, `IDownstreamApi`, and the role of `EnableTokenAcquisitionToCallDownstreamApi`:  
  - https://learn.microsoft.com/en-us/Azure/active-directory/develop/scenario-web-app-call-api-overview
- App configuration for calling downstream APIs (`BaseUrl`, `Scopes` and `.AddDownstreamApi(...)`):  
  - https://learn.microsoft.com/en-us/entra/identity-platform/scenario-web-app-call-api-app-configuration
- API-side configuration example chaining `.EnableTokenAcquisitionToCallDownstreamApi().AddDownstreamApi(...)`:  
  - https://learn.microsoft.com/en-us/entra/identity-platform/scenario-web-api-call-api-app-configuration

## Incorrect Assumptions (Explicit)

1. **“AppHost can be a normal console project with a package reference”**  
   Reality: Aspire AppHost projects are expected to use the Aspire AppHost SDK and be configured via launch profiles for dashboard/OTLP in typical dev setups. See Aspire SDK/AppHost configuration docs above.

2. **“If we use `Authority = .../v2.0`, tokens will always have a v2 issuer.”**  
   Reality: access tokens can still be v1 (`iss = https://sts.windows.net/...`) and Microsoft docs explain both issuer formats. Our backend validation must be compatible with the token versions we actually receive (or we must enforce token version to be v2).

3. **“EnableTokenAcquisitionToCallDownstreamApi automatically attaches tokens to HTTP calls.”**  
   Reality: it enables the services; you still call `IDownstreamApi` or `ITokenAcquisition` and ensure the bearer token is used for the specific request.

## Action Items / Guardrails

- Prefer Microsoft.Identity.Web helpers on both sides where possible:
  - For APIs, consider using `AddMicrosoftIdentityWebApi(...)` which handles many token validation details.
- When debugging 401s:
  - Confirm first whether the backend is missing the Authorization header vs rejecting a token; JwtBearer events/logs are invaluable.
  - Decode the token (`iss`, `aud`, `scp`, `ver`) and compare to the backend’s validation parameters.
- Keep `launchSettings.json` under source control for AppHost so devs don’t need to guess dashboard/OTLP env vars.
